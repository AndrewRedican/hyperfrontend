# @hyperfrontend/integration-nx

The workspace's boundary with Nx. Everything that knows Nx's shapes or calls Nx lives here, so the rest of the workspace compiles against this package and nothing else imports `@nx/devkit`. The package is private and never published; it has no build.

| Entry                                     | Holds                                                                                                                                                                                              | Imports Nx?                                  |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `@hyperfrontend/integration-nx/model`     | The workspace's own vocabulary: `ProjectFile`, `NxJsonFile`, `TargetDefinition`, `InputDefinition`, `WorkspaceProject`, `TaskRef`. The subset of `nx.json` and `project.json` the workspace reads. | No                                           |
| `@hyperfrontend/integration-nx/compat`    | Generated declarations compatible with `@nx/devkit`: `ExecutorContext`, `PromiseExecutor`, `Tree`, `ProjectGraph`, `CreateNodesV2` and what they reference.                                        | No; the files are copied from Nx's sources   |
| `@hyperfrontend/integration-nx/adapters`  | The runtime code that calls Nx: `loadDevkit` resolves a workspace's `@nx/devkit` without a static import, `nxRunner` runs its `nx` headless, `readNxGraph` reads the graph Nx computes.            | Lazily, through `createRequire` or a process |
| `@hyperfrontend/integration-nx/manifests` | The `executors.json` and `generators.json` shapes Nx discovers, and `validateExecutorsManifest` / `validateGeneratorsManifest` checking every entry can be read.                                   | No                                           |

## Generated declarations

`src/compat/executor.ts`, `graph.ts`, `tree.ts`, `plugin.ts`, `index.ts`, `REPORT.md` and `NOTICE.md` are generated by the type-extraction tool in `tools/workspace` from Nx's TypeScript sources on GitHub at the tag `tools/workspace/types-extract.config.ts` names, resolved once to a commit and pinned in `tools/workspace/types-extract.lock.json`. Each file's header carries the commit, the upstream files it was copied from, the roots and depth requested, and the upstream copyright; `NOTICE.md` reproduces the MIT license. Do not edit them by hand: the check regenerates them in memory and fails on any byte that differs.

```bash
npx nx run tool-workspace:types-extract
npx nx run tool-workspace:types-extract-check
```

The declarations are copied as written, with a few deliberate rewrites that `REPORT.md` lists one by one: a reference deeper than the request follows, or to a declaration the configuration names as never carried, is written as `unknown` or as the configured replacement; `any` becomes `unknown`; an untyped parameter is annotated; an enum becomes the union of its values; a class becomes the interface of its public instance members. The release, sync, migrate and installation settings of `nx.json` and the package manifest shape are carried as `Record<string, unknown>`, since the executors never read them.

`src/compat/compat.spec.ts` assigns a hand-written executor context to the generated type and, in both directions, to the `@nx/devkit` types the workspace installs. It is the one place a real Nx type appears, and it fails the type check if the generated subset drifts from the installed devkit.

## Consumers

The executors of `@hyperfrontend/app`, `@hyperfrontend/package` and `@hyperfrontend/workspace` type their context and signature from `compat`. The affected-baseline replay in `tools/workspace` runs Nx through `adapters`. The `version-batch` executor still calls `createProjectGraphAsync` from `@nx/devkit` until the owned graph replaces it, and the generators of `@hyperfrontend/package` still use the devkit tree helpers.

## Tags

`type:integration`, `scope:internal`. An integration package may depend on `type:core` and `type:util` libraries; `type:util` and `type:protocol` projects may depend on it.
