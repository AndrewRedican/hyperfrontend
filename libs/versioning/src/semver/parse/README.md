# parse

Version and range parsing, with both strict and permissive variants.

`parseVersion(input)` reads a full major.minor.patch version with optional prerelease and build identifiers, tolerating surrounding whitespace and a leading `v` or `=`, and returns a [`ParseVersionResult`](https://www.hyperfrontend.dev/docs/libraries/versioning/semver/parse/#api-ParseVersionResult) that reports a failure instead of throwing; [`parseVersionStrict`](https://www.hyperfrontend.dev/docs/libraries/versioning/semver/parse/#api-parseVersionStrict) applies the same rules and returns the [`SemVer`](https://www.hyperfrontend.dev/docs/libraries/versioning/semver/models/#api-SemVer) itself, throwing on input it cannot read. [`coerceVersion`](https://www.hyperfrontend.dev/docs/libraries/versioning/semver/parse/#api-coerceVersion) is the permissive option: it pulls a usable version out of inputs like `"v1"`, `"1.2"`, or `"1.2.3.4"` for use cases where semver-ish input must be normalized, and returns `null` when there is nothing to read.

[`parseRange`](https://www.hyperfrontend.dev/docs/libraries/versioning/semver/parse/#api-parseRange) and [`parseRangeStrict`](https://www.hyperfrontend.dev/docs/libraries/versioning/semver/parse/#api-parseRangeStrict) are the same pair for range syntax (`^1.2.0`, `~1.2`, `18 || 20`, `>=1.0.0 <2.0.0`, `1.0.0 - 2`, ...), read the way npm reads it: a part left out or written as `x` or `*` stands for every value it could take, so `18` admits all of 18 and `>1.2` starts at 1.3.0. The first returns a [`ParseRangeResult`](https://www.hyperfrontend.dev/docs/libraries/versioning/semver/parse/#api-ParseRangeResult) carrying either the parsed [`Range`](https://www.hyperfrontend.dev/docs/libraries/versioning/semver/models/#api-Range) or the reason it failed; the second returns the [`Range`](https://www.hyperfrontend.dev/docs/libraries/versioning/semver/models/#api-Range) or throws.
